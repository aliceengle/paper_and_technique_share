1. 结论摘要

1.1 不存在脱离算法和服务后端的唯一最优框架

场景 第一选择 第二选择 核心原因
延续当前项目的 vLLM + DSpark Speculators TorchSpec Speculators 已有本项目双 B200 在线训练实证，checkpoint 可由 vLLM 自描述直载；迁移收益必须大于重新验证成本
新建 SGLang + Domino SpecForge NeMo AutoModel SpecForge 原生 Domino，在线/离线配置和 SGLang + Mooncake 数据面完整；AutoModel 能训练但自带 serving helper 明确没有 Domino runtime 闭环
新建 SGLang + DSpark SpecForge TorchSpec SpecForge 对 DSpark 有大量在线/离线/SGLang 配置；TorchSpec 的 SGLang hidden-state backend 为社区支持级别
新建 vLLM + DSpark，且需要多推理后端供数 TorchSpec Speculators TorchSpec 可在 vLLM、SGLang、TensorRT-LLM、HF 之间选择 target 供数；Speculators 的 vLLM 链路更短
Qwen3.8-27B + DFlash2 精确复现 NeMo AutoModel TorchSpec AutoModel 有 Qwen3.8-27B 专用 recipe、DFlash2 模型类与测试；TorchSpec 更适合进一步改造成推理池/训练池解耦
DFlash2 解耦式在线训练 TorchSpec NeMo AutoModel TorchSpec 原生 DFlash2 trainer，并以 Ray + Mooncake 解耦 vLLM/SGLang target 与 FSDP2 trainer；AutoModel 的 DFlash2 当前以 co-located target 为主
超大 MoE、复杂 TP/CP/EP/FSDP2 训练 NeMo AutoModel SpecForge AutoModel 通用分布式训练能力和模型覆盖最广；代价是 Draft 子系统的部署闭环不均衡、工程栈更重

建议采用“一个生产主线 + 两个按需实验轨道”：

  1. 现有 GLM-5.2 DSpark 生产主线继续使用 Speculators，不为框架统一而迁移。
  2. DFlash2 建立 TorchSpec/NeMo AutoModel 实验轨道：前者验证解耦在线吞吐，后者作为 Qwen3.8 架构正确性基线。
  3. 如果生产服务明确转向 SGLang，再将 SpecForge 作为 Domino、DSpark 和 DFlash 的主线框架。

2.3 “在线训练”需要拆成三种不同含义

本文的在线训练不是强化学习意义上的“参数更新后立即重新采样”。这里主要指 target supervision 是否在 Draft 训练期间按需产生：

训练形态 Target hidden states 来源 是否长期落盘 典型拓扑
Co-located online 冻结 target 与 Draft trainer 同进程或同一 GPU 组执行 否 NeMo AutoModel DFlash family 默认路径
Disaggregated online 外部 vLLM、SGLang、TensorRT-LLM 或 target service 按需生成，经 Mooncake/NCCL/文件传输 否 Speculators、SpecForge、TorchSpec
Offline target cache 先生成 hidden states/logits，再停 target、重复训练 是 四框架均有不同程度支持
Hybrid 第一个 epoch 在线生成并缓存，后续 epoch 重放 是 Speculators 原生

训练数据中的 answer 仍应来自目标模型的 on-policy regeneration。在线 hidden-state capture 并不会自动修复“answer 由另一个模型生成”的分布偏移。

4.2 磁盘和算力的近似关系

若样本数为 $N$、平均序列长度为 $L$、抽取层数为 $m$、hidden size 为 $H$、每元素字节数为 $b$，忽略 token IDs、索引和文件系统开销，离线 cache 量级为：

$$ S_{\text{offline}} \approx N L m H b $$

在线模式的稳态缓存只与最大在途样本数 $C$ 有关：

$$ S_{\text{online, steady}} \approx C L m H b, \qquad C \ll N $$

因此多 epoch 时，离线方案用磁盘换取 target forward 只执行一次；纯在线方案几乎不占长期磁盘，但每个 epoch 都重新承担 target forward、排队和传输成本。Hybrid 在第一个 epoch 支付生成成本，随后转为离线重放。

4.4 在线训练为什么值得优先评估

原因 在线训练的价值 风险
样本多、序列长、抽取层多 不产生全量 target cache，避免 TB/PB 级容量和跨机拷贝 target 推理可能成为 trainer 等待瓶颈
数据或 loss mask 频繁变化 不必反复重建 cache 必须保证 target revision、layer IDs 和 token 对齐
推理池和训练池可独立扩缩 可按 target throughput 与 trainer throughput 分别扩容 控制面、backpressure、超时、对象回收更复杂
希望快速切换算法 同一 target capture 可服务不同 Draft trainer 不同算法所需 hidden/logits schema 可能不同，不能盲目复用

当前项目的 8192-token、多个 hidden layer、百万级样本场景符合在线训练的容量优势；但必须同时测量 target forward、传输、排队和 trainer compute，而不能只看网络带宽。

6.3 为什么不能把“可适配”写成“已支持”

Speculators 的 schema 中出现 dflash2 字符串，但官方 decision guide 明确只列 EAGLE-3、P-EAGLE、DFlash、DSpark、MTP 五种算法，且没有 DFlash2 模型、loss、trainer 或测试。因此这只是预留痕迹。

同理，SpecForge 的 DFlash-family 公共模型不能自动得到 DFlash2：DFlash2 还需要每个子层的动态短卷积、selector codebook、top-K 前驱条件 loss 和对应 checkpoint layout。缺少这些模块就不能称为支持。

SpecForge 非主线 ✅ 第一方生态；EAGLE3 有专用 key 校验 exporter，DFlash family 走 HF export DFlash/Domino/DSpark 仍需对目标 SGLang commit 做加载与 acceptance gate
TorchSpec ✅ --vllm 导出 key/config ✅ 默认 native key 面向 SGLang 有转换器但无统一 serve 教程；算法 runtime 和 engine 版本需独立核验
NeMo AutoModel EAGLE3/P-EAGLE/DFlash 较完整 EAGLE family 较完整 DFlash2 已有引擎上游 runtime，但 AutoModel helper 尚未接线；Domino 无现成 runtime；DSpark helper 尚未闭环

本项目已有技术报告确认 DFlash2 的 SGLang PR #35371 与 vLLM PR #52816 已合并。这证明引擎具备 DFlash2 runtime，不代表每个训练框架导出的 checkpoint 都已经通过 shape/key/采样一致性验证。

9. 单框架详评

9.1 Speculators

适合： 已使用 vLLM、希望以最少转换部署 EAGLE3/DFlash/DSpark/P-EAGLE/MTP，或已有 Speculators checkpoint/数据资产的团队。

优点 局限
Online/Offline/Hybrid 三模式统一，当前 upstream 已提供多节点 Mooncake connector target capture 和 serving 均高度绑定 vLLM
checkpoint 自描述，vLLM 可直接加载 不支持 DFlash2、Domino
FSDP、checkpoint resume、数据 packing、词表裁剪、真实 acceptance evaluation 完整 新算法支持速度受 vLLM runtime 与 Speculators schema 双重约束
本项目 GLM-5.2 DSpark 已完成在线 Mooncake 实证 本地历史补丁与当前 upstream 接口已发生演进，升级需重新做 parity

本项目的已验证链路见：Speculators GLM-5.2 DSpark 训练指南 和 双 B200 在线 Mooncake 训练复盘。这类实证应在当前 DSpark 选型中获得高于 GitHub Star 的权重。

9.2 SpecForge

适合： 服务端确定为 SGLang，需要 Domino/DSpark/DFlash/EAGLE3，并希望在线/离线统一为 producer/consumer runtime 的团队。

优点 局限
SGLang 团队维护，Domino/DSpark 配置、测试和模型覆盖密集 没有 DFlash2
在线 target 不进入 trainer；SGLang 直接写 Mooncake，控制面只传引用 online 目前必须 disaggregated，无简单 colocated online 路径
external/managed-local、多 capture server、多节点 consumer、backpressure 和失败恢复设计完整 SGLang capture 需要版本钉定或 patch；不是纯 upstream 无侵入
typed run config 和 algorithm contract 能较早拒绝不支持组合 vLLM 不是第一方 target 或 serving 路径

生产使用应钉定 commit，而不是只写 pip install 浮动版本：当前 README 的 v0.3.0 新闻、仓库 version.txt=0.2.0 与 GitHub 无 Release/tag 三者并不完全一致。

9.3 TorchSpec

适合： 需要 vLLM/SGLang/TensorRT-LLM 多 target backend，推理池与训练池独立扩缩，或计划训练 DFlash2/DSpark 的团队。

优点 局限
Ray actor + Mooncake + FSDP2，天然解耦 inference 和 training 运行栈最复杂之一，需要 Ray、Mooncake、引擎 patch/worker extension 协同排障
DFlash2 和 DSpark 均有独立 model/trainer/config/test 不支持 Domino
vLLM、TensorRT-LLM 是 first-class target backend；SGLang/HF 也可用 SGLang 标为 best community effort；DFlash2 仍是主分支新能力、无 Release
转换器区分 vLLM 与 SGLang key，并对 DFlash2 做 serving config fixup offline replay 尚未优化，且训练时仍需要 target embedding/norm/LM-head 权重

TorchSpec 的 Offline 文档给出 Qwen3-8B DFlash 1000 样本约 6 GB 的示例，说明其离线路径更适合开发和回归，而不是当前百万样本的默认生产方案。

9.4 NeMo AutoModel

适合： 需要最广模型覆盖、Qwen3.8 DFlash2 现成 recipe、复杂模型并行，或希望在统一 NVIDIA 训练平台内开发新 Draft 方法的团队。

优点 局限
四框架中唯一同时原生训练 DFlash2、Domino、DSpark 三算法的 serving helper 均未达到 EAGLE 同等成熟度
Qwen3.8-27B DFlash2 专用配置，动态卷积和 selector 参数完整 DFlash2/Domino 当前以 co-located target 为主，不具备 TorchSpec 式通用 vLLM/SGLang capture
DDP/FSDP2/TP/CP/EP、FP8、LoRA、sequence packing 和大 MoE 能力丰富 平台体量大、依赖重、升级面宽
EAGLE3/DSpark 支持 offline cache，大 DSpark target 可分布式 precompute 各算法的数据模式、并行组合和服务兼容性不对称，必须逐 recipe 核验

AutoModel 更适合作为“能力最广的训练平台”，不应因为算法列表最长就直接视为“最短生产路径”。

10.1 当前项目的推荐组合

层次 推荐 说明
生产基线 Speculators + vLLM + DSpark 复用已经跑通的在线 Mooncake、checkpoint、评估与恢复链路
DFlash2 算法基线 NeMo AutoModel + Qwen3.8 recipe 先冻结 shape、loss、selector 和动态卷积正确性
DFlash2 规模化在线实验 TorchSpec + vLLM/SGLang target pool 验证 inference/training 独立扩缩与 Mooncake 稳态吞吐
SGLang 新路线 SpecForge + Domino/DSpark 复用 SGLang capture、Mooncake 和 typed topology

10.2 不建议立即统一到一个框架

统一框架只有在数据、checkpoint、评估和 serving 都能降低长期维护成本时才有价值。当前三个重点算法的最优路径分散在不同项目中，强行统一会引入以下额外工作：

  • 重新实现缺失算法，例如在 Speculators 中补 DFlash2/Domino；
  • 重新验证 checkpoint key、sampling、acceptance 和拒绝采样分布；
  • 重新排查 target hidden state 的层号、prenorm/postnorm 与词表映射；
  • 重新建立在线失败恢复、backpressure、Mooncake 对象回收和多机部署脚本。

因此近期更合理的是统一 验收协议，而不是统一训练代码库。

11. 建议的统一验收协议

11.1 分阶段 Gate

Gate 目标 必须产出 通过条件
G0 静态准入 核对 target、tokenizer、Draft config、layer IDs 和版本 resolved config、commit、权重 hash 无隐式默认值漂移，架构和词表一致
G1 单卡/双卡离线 smoke 验证 forward、loss、backward、save/resume 100～1000 样本日志和 checkpoint loss 有限、梯度非零、重启后 step 连续
G2 在线 1 小时 验证 target capture、传输、回收和 backpressure target/trainer/transfer 分项耗时 无持续对象泄漏，无样本静默丢失
G3 Checkpoint 服务 在目标 vLLM/SGLang 加载 启动命令、服务日志、首请求结果 key/shape 全部匹配，无 silently skipped weights
G4 质量与性能 与无 Draft baseline 同口径比较 acceptance length、逐位置接受率、吞吐、P50/P99 输出分布正确，且目标并发下有净收益
G5 故障恢复 注入 target 重启、网络超时、trainer 中断 恢复日志和最终 hash 不重复更新、不漏样本、checkpoint 可恢复

11.2 公平 A/B 的固定变量

类别 固定项
Target 相同模型 revision、精度、tokenizer、chat template 和推理参数
数据 相同 target-regenerated answers、train/val split、max tokens 和 loss mask
Draft 相同参数量量级、block/depth、词表口径和训练 token 数
训练 相同 optimizer、学习率计划、有效 batch tokens 和 epoch 数
服务 相同 vLLM/SGLang commit、GPU、TP、并发、上下文长度和采样参数
指标 step time 必须拆 target generation、queue、transfer、trainer compute、checkpoint

12. 最终建议

如果现在就开始训练：

  1. 已有 vLLM + DSpark 工程不迁移，继续 Speculators。 当前项目已有比公开 README 更有价值的双机在线证据。
  2. Qwen3.8-27B DFlash2 先用 NeMo AutoModel 做小规模正确性基线。 它是四者中唯一提供该模型专用 DFlash2 recipe 的框架。
  3. 随后用 TorchSpec 验证 DFlash2 解耦在线训练。 重点不是再次证明模型能收敛，而是测清 vLLM/SGLang target pool、Mooncake 和 FSDP2 trainer 的吞吐平衡。
  4. 如果目标服务确定为 SGLang，Domino/DSpark 默认选 SpecForge。 其优势来自训练拓扑和服务生态一致，而不只是 Star 数最高。
  5. NeMo AutoModel 保留为大模型/复杂并行平台。 在 DFlash2、Domino、DSpark 的 serving helper 补齐前，不把“能训练”误写成“可直接生产部署”。

一句话总结：

Speculators 是当前 vLLM + DSpark 的最稳生产基线；SpecForge 是 SGLang + Domino/DSpark 的最佳匹配；TorchSpec 是 DFlash2/DSpark 解耦在线训练的最强候选；NeMo AutoModel 是算法和模型覆盖最广、但部署闭环最不均衡的大型训练平台。

13. 局限性

  • 本文是 2026-08-25 快照；四个仓库都处于快速演进期，尤其 TorchSpec DFlash2 是主分支新能力。
  • 本轮没有在同一组 GPU、同一 target 和同一数据上重新训练四框架，不能据本文直接断言谁的 tokens/s 最高。
  • 框架文档中的“支持 vLLM/SGLang”可能指 target hidden-state capture，也可能指训练后 serving；本文已尽量拆分，但最终仍以实际加载和 acceptance gate 为准。
  • GitHub Star、提交数和测试文件数是维护信号，不是精度、吞吐或稳定性的替代指标。
  • 对未发现支持的判断仅限冻结 commit，不代表项目未来不会加入，也不排除未合并分支或第三方实现。
